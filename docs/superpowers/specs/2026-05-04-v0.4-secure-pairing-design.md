# v0.4 SPAKE2 安全配对 + mDNS 发现 设计规格

## 目标

为 screen-mirror 添加零配置设备发现和密码认证密钥交换（PAKE），实现：
1. 接收端通过 mDNS 自动广播服务，发送端无需手动输入 IP
2. 每次投屏需输入 6 位数字码完成 SPAKE2+ 认证
3. 所有控制和媒体流量使用 ChaCha20-Poly1305 加密

## 架构概览

```
Receiver (displays PIN)              Sender (enters PIN)
─────────────────────                ─────────────────────
mDNS advertise                       mDNS browse
  _screenmirror._tcp                   discover receiver
  SRV → dynamic port                  
  TXT → device_name                  

TCP listener (dynamic port)     ←──  TCP connect
                                     
SPAKE2+ exchange (3 rounds)     ←→   SPAKE2+ exchange
  verifier derived from PIN            uses PIN directly
                                     
HKDF-SHA256 derive keys              HKDF-SHA256 derive keys
  key_control (TCP)                    key_control (TCP)
  key_media (UDP)                      key_media (UDP)

Encrypted Offer/Answer          ←→   Encrypted Offer/Answer
  (JSON capability negotiation)        

Encrypted media stream          ←──  UDP encrypted RTP
Encrypted control messages      ←→   TCP encrypted JSON
```

## 模块设计

### 1. mDNS 服务发现

**服务类型：** `_screenmirror._tcp.local.`

**接收端（广播）：**
- 启动时注册 mDNS 服务
- SRV 记录指向动态 TCP 端口（OS 分配）
- TXT 记录仅包含 `device_name=<hostname>`
- 有活跃连接时取消广播（仅允许单连接）
- 连接断开后重新注册广播

**发送端（浏览）：**
- 持续浏览 `_screenmirror._tcp` 服务
- 展示发现的设备列表（device_name + IP）
- 用户选择设备后发起 TCP 连接

**Rust crate：** `mdns-sd`（纯 Rust，跨平台，支持 macOS/Windows/Linux）

### 2. SPAKE2+ 认证（RFC 9382）

**PIN 码生命周期：**
- 接收端无活跃连接时，始终在屏幕上显示一个随机 6 位数字码
- 配对成功后，PIN 从屏幕消失
- 连接断开后（无论原因），立即生成新的 6 位码并显示
- 无错误次数限制，PIN 输错不锁定

**协议流程（3 轮）：**

```
Sender                              Receiver
──────                              ────────
                                    (displays PIN "847291")
User enters PIN
                                    
Round 1:
  pA = SPAKE2+.compute_message()
  ──── pA ────────────────────→
                                    pB = SPAKE2+.compute_message()
  ←─── pB ────────────────────
                                    
Round 2:
  Both compute shared secret K
  confirmS = HMAC(K, transcript)
  ──── confirmS ──────────────→
                                    Verify confirmS
                                    confirmR = HMAC(K, transcript)
  ←─── confirmR ──────────────
  Verify confirmR
                                    
Round 3 (implicit):
  Both derive session keys via HKDF
```

**密码处理：**
- PIN 作为 password 直接传入 SPAKE2+（UTF-8 编码的 6 位数字字符串，如 `b"847291"`）
- `spake2` crate 内部处理 password 到群元素的映射

**身份标识：**
- Sender identity: `b"sender"` (固定)
- Receiver identity: `b"receiver"` (固定)
- 无需设备标识，因为每次都重新配对

**Rust crate：** `spake2` (RustCrypto 生态)

### 3. 密钥派生（HKDF-SHA256）

从 SPAKE2+ 共享密钥 K 派生两个独立密钥：

```
key_control = HKDF-Expand(K, info="screenmirror-control-v1", len=32)
key_media   = HKDF-Expand(K, info="screenmirror-media-v1",   len=32)
```

- `key_control`: 加密 TCP 控制通道
- `key_media`: 加密 UDP 媒体通道
- Salt: 空（SPAKE2+ 输出已经是高熵的）

**Rust crate：** `hkdf` + `sha2` (RustCrypto)

### 4. 加密方案：ChaCha20-Poly1305

统一用于 TCP 控制和 UDP 媒体两个通道。

#### TCP 控制通道加密

帧格式（length-prefixed）：
```
[4B length | 8B nonce_counter | encrypted_payload | 16B auth_tag]
```

- length: 包含 nonce_counter + encrypted_payload + tag 的总长度（大端 u32）
- nonce: 12 字节 = 4B 固定前缀 `0x00000000` + 8B counter（大端）
- 每个方向独立维护 counter（发送方递增自己的 counter）

#### UDP 媒体通道加密

帧格式：
```
[8B nonce_counter | encrypted(RTP_header + RTP_payload) | 16B auth_tag]
```

- 整个 RTP 包（header + payload）作为明文加密
- nonce: 12 字节 = 4B 固定前缀 `0x00000001` + 8B counter（大端）
- 每个 SSRC 方向独立维护 counter

**加密开销：** 每个 UDP 包增加 24 字节（8B counter + 16B tag）

**Rust crate：** `chacha20poly1305` (RustCrypto)

### 5. 重放保护

**UDP 媒体通道：**
- 基于 8 字节单调递增 counter
- 接收端维护滑动窗口（窗口大小 = 2048 packets）
- 窗口内的包：检查 bitmap 判断是否重复
- 窗口之前的包（counter < window_base）：直接丢弃
- 窗口之后的包：滑动窗口前进

**TCP 控制通道：**
- TCP 本身保证有序，仅需检查 counter 严格递增
- counter 不递增 → 关闭连接

### 6. 能力协商（Offer/Answer）

SPAKE2+ 完成后，通过加密 TCP 通道交换 JSON 消息：

**Sender → Receiver: Offer**
```json
{
  "type": "offer",
  "video": {
    "codec": "h264",
    "width": 2560,
    "height": 1440,
    "fps": 60,
    "bitrate": 20000000
  },
  "audio": {
    "codec": "opus",
    "sample_rate": 48000,
    "channels": 2,
    "bitrate": 128000
  },
  "transport": {
    "udp_port": 5004,
    "fec_group_size": 6
  }
}
```

**Receiver → Sender: Answer**
```json
{
  "type": "answer",
  "video": {
    "codec": "h264",
    "max_width": 1920,
    "max_height": 1080,
    "max_fps": 60
  },
  "audio": {
    "codec": "opus",
    "sample_rate": 48000,
    "channels": 2
  },
  "transport": {
    "udp_port": 5004
  }
}
```

Sender 收到 Answer 后，取 min(offer, answer) 确定最终参数，开始推流。

### 7. 连接生命周期

```
状态机（接收端）:

  IDLE (显示PIN, mDNS广播)
    │
    ├─ TCP连接到达 → PAIRING (停止mDNS广播)
    │
    ├─ SPAKE2+失败 → IDLE (生成新PIN)
    │
    └─ SPAKE2+成功 → NEGOTIATING
                        │
                        ├─ Offer/Answer完成 → STREAMING (PIN隐藏)
                        │
                        └─ 超时/失败 → IDLE (生成新PIN)

  STREAMING
    │
    ├─ TCP断开（任一端）→ IDLE (销毁密钥, 生成新PIN)
    │
    ├─ 收到disconnect消息 → IDLE (销毁密钥, 生成新PIN)
    │
    └─ 用户点击"断开" → 发送disconnect → IDLE
```

**超时：**
- PAIRING 阶段：10 秒内未完成 SPAKE2+ → 断开
- NEGOTIATING 阶段：5 秒内未完成 Offer/Answer → 断开

### 8. 强制断开

**发送端断开：**
- UI 提供"断开连接"按钮
- 发送加密控制消息：`{"type":"disconnect","reason":"sender_initiated"}`
- 不等待响应，直接关闭 TCP 连接
- 销毁本地会话密钥

**接收端断开：**
- UI 提供"断开连接"按钮
- 发送加密控制消息：`{"type":"disconnect","reason":"receiver_initiated"}`
- 关闭 TCP 连接
- 销毁会话密钥 → 生成新 PIN → 回到 IDLE

**异常断开：**
- TCP 连接意外关闭（网络断开、进程崩溃）
- 检测方式：TCP keepalive（间隔 5s，超时 15s）
- 检测到断开后与正常断开相同处理

### 9. 控制消息定义

所有控制消息通过加密 TCP 通道传输，JSON 格式：

```json
{"type": "disconnect", "reason": "sender_initiated|receiver_initiated"}
{"type": "ping"}
{"type": "pong"}
{"type": "bitrate_adjust", "bitrate": 15000000}
```

Ping/Pong 用于应用层心跳（每 2 秒），补充 TCP keepalive。

### 10. 安全属性

| 属性 | 保证 |
|------|------|
| 认证 | SPAKE2+ 抵抗离线字典攻击，即使 6 位码 |
| 前向保密 | 每次配对生成新密钥，无法用旧会话密钥解密 |
| 中间人保护 | SPAKE2+ confirmation 阶段检测 MITM |
| 重放保护 | 单调 counter + 滑动窗口 |
| 密钥隔离 | 控制/媒体使用不同 HKDF 派生密钥 |
| 密钥销毁 | 断开连接后立即 zeroize 所有密钥材料 |

### 13. 不做什么（显式排除）

- 不做信任持久化（不记住设备、不存证书）
- 不做多连接支持（始终单一连接）
- 不做 PIN 错误锁定
- 不做 DTLS/TLS（自建加密层更轻量）
- 不做 NAT 穿透（v0.4 仅局域网）
- 不做视频/音频编解码变更（复用 v0.3）
