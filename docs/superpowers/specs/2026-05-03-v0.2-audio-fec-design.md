# v0.2 音频 + 基础传输优化 — 设计文档

## 概述

在 v0.1 纯视频管线基础上，加入系统音频捕获与 Opus 编码、音视频同步、逐帧 XOR FEC 前向纠错、音频 Jitter Buffer，实现完整的音视频投屏体验。

**目标延迟**：端到端 <100ms（含音频路径）。

**验收标准**：
- 音视频同步偏差 < 40ms
- 模拟 2% 丢包率下画面不花屏
- 音频无爆音、无卡顿

---

## 系统架构

```
发送端 (sender)
┌───────────────────────────────────────────────────────┐
│ ScreenCaptureKit Stream                               │
│   ├─ Video callback                                   │
│   │   pts → RTP ts (90kHz)                           │
│   │   → VTEncoder → H264 NALs → Packetizer          │
│   │   → FEC group (XOR, per-frame) → UDP send        │
│   └─ Audio callback                                   │
│       pts → RTP ts (48kHz)                           │
│       → Opus encode (CELT, 128kbps, 10ms, DTX)       │
│       → RTP pack → FEC group (XOR, per-6-pkt)       │
│       → UDP send                                      │
└───────────────────────────────────────────────────────┘

接收端 (receiver)
┌───────────────────────────────────────────────────────┐
│ UDP recv → 按 PT 分流                                 │
│                                                       │
│ Video path (PT=96):                                   │
│   → 丢包检测 → FEC 恢复 → H264 Depacketize          │
│   → VTDecoder → 1-frame buffer → MetalRenderer       │
│                                                       │
│ Audio path (PT=111):                                  │
│   → 丢包检测 → FEC 恢复 → Opus decode (含 PLC)      │
│   → 40ms Jitter Buffer → CoreAudio AudioUnit output  │
│                                                       │
│ FEC data (PT=127):                                    │
│   → 存入对应 group 的 FEC 恢复表                      │
│                                                       │
│ Sync: 音频播放位置为主时钟                             │
│   drift > ±30ms → 音频重采样微调 ±2% 校正            │
└───────────────────────────────────────────────────────┘
```

## 音频捕获与编码

### 捕获

ScreenCaptureKit 的 `SCStreamOutput` 回调支持 `SCStreamOutputType::Audio`。复用现有 `MacOsCapture` 的 SCStream，新增音频 output handler，通过独立 channel 发送音频 CMSampleBuffer。

音频回调输出格式：PCM Float32, 48kHz, Stereo。

### Opus 编码参数

| 参数 | 值 | 依据 |
|------|------|------|
| Application | CELT (LowDelay) | RFC 6716: CELT 适合混合内容（音乐+语音+UI音效） |
| 码率 | 128kbps Stereo | scrcpy、Chrome Remote Desktop 行业共识 |
| 帧大小 | 10ms (480 samples) | RustDesk、Sunshine 共识；12.5ms 总编解码延迟 |
| 采样率 | 48kHz | Opus 原生采样率 |
| 声道 | Stereo | Steam Remote Play 也仅 Stereo |
| DTX | 启用 | 静态桌面时带宽降 90% |
| In-band FEC | 禁用 | 传输层 XOR FEC 已保护音频包；Opus FEC 额外开销 ~2/3 码率不值得 |

### Rust crate

使用 `opus` crate（libopus 绑定）或 `magnum-opus`（RustDesk 验证过）。

### RTP 打包

- Payload Type: 111
- 时钟频率: 48,000 Hz
- 每包 1 个 Opus 帧（~160 bytes payload，远小于 MTU）
- SSRC: 独立于视频流（不同随机值）

## 逐帧 XOR FEC

### 论文支撑

| 论文 | 结论 |
|------|------|
| Tooth (NSDI 2025) | 固定窗口 FEC 跨帧边界导致帧级丢包率 10× 方差 |
| TAROT (MMSys 2026) | 静态 FEC 在大帧浪费 5-9× 冗余 |
| Haivision ARQ vs FEC | LAN 25% FEC 冗余在 2% 丢包下实现 99.5% 恢复率 |
| RFC 8854 | FEC 在延迟敏感场景优于 NACK（零 RTT 依赖） |

### 视频 FEC

- FEC 分组 = 帧边界（RTP marker bit 标记帧结束）
- 一帧的所有 RTP 包构成一个 FEC group
- 每 6 个数据包生成 1 个 XOR FEC 包（~15% 冗余）
- 若帧 <6 包，则该帧所有包 XOR 为一个 FEC 包
- XOR 限制：每组仅恢复 1 个丢包（LAN 6 包中丢 ≥2 概率 <0.1%）

### 音频 FEC

- 按 sequence number 连续计数，每 6 个音频 RTP 包为一组
- 组满（收到第 6 个包）时立即生成并发送 1 个 XOR FEC 包
- 独立于视频 FEC group（音频和视频各自维护 seq 计数器）

### FEC 包格式

```
[RTP Header (PT=127)] [FEC Header (4 bytes)] [XOR Payload]

FEC Header:
  - base_seq: u16  — group 起始 sequence number
  - group_len: u8  — group 中数据包数量
  - media_pt: u8   — 被保护的媒体 PT (96=video, 111=audio)
```

### 接收端恢复管线

```
UDP recv
  → 按 PT 分流
  → PT=127: 存入 FEC group 表
  → PT=96/111: 存入 RTP buffer，检测 seq gap
  → gap 检测到且 FEC 包已到: XOR 恢复缺失包
  → 恢复后的包送入 depacketizer（视频）或 Opus decoder（音频）
```

## 音视频同步

### 论文支撑

| 来源 | 结论 |
|------|------|
| ITU-R BT.1359-1 | 音频超前视频 ≤45ms、滞后 ≤125ms 为可检测阈值；±30ms 不可感知 |
| ACM SIGCOMM 2023 Ekho | 20ms 延迟差即可降低质量感知 |
| FFplay 参考实现 | 最小阈值 40ms，最大 100ms，速率调整 ±10% |
| scrcpy | buffer 水位线 + swr_set_compensation 重采样漂移校正 |
| Apple Developer Forums | ScreenCaptureKit pts 与系统时钟不同时钟域 |

### 发送端

1. 音频/视频回调的 `presentationTimeStamp` 转换为 RTP 时间戳：
   - 视频: `rtp_ts = pts_ns * 90000 / 1_000_000_000`
   - 音频: `rtp_ts = pts_ns * 48000 / 1_000_000_000`
2. 两路流 RTP 时间戳基于同一 SCK pts 参考（内部一致性）

### 接收端同步策略

- **主时钟**：音频播放位置（CoreAudio 回调的 sample counter 单调递增）
- **漂移检测**：追踪 `(video_rtp_ts 换算壁钟) - (audio_playback_position 换算壁钟)` 的差值
- **校正阈值**：|drift| > 30ms
- **校正方式**：音频重采样微调 ±2%（scrcpy 方案）
  - drift > +30ms（视频超前）：加速音频播放 102%
  - drift < -30ms（音频超前）：减速音频播放 98%
  - 微调持续直到 |drift| < 10ms 后恢复 100%
- **极端情况**：|drift| > 200ms → 重置同步（丢弃 buffer，重新对齐）

### 为什么不用 RTCP SR

LAN 单发送端→单接收端，音视频从同一台机器的同一个 SCK stream 捕获，共享相同的 pts 时钟域。RTCP SR 适用于多源/跨网络场景，v0.2 不需要。

## Jitter Buffer

### 视频：1 帧缓冲

- 收到完整帧后不立即渲染，暂存 1 帧深度
- 下一帧到达时渲染前一帧（流水线）
- 缓冲 > 3 帧时丢弃最旧帧追赶
- 增加延迟：~16ms (60fps)，总延迟仍 <100ms
- 依据：JitBright (ACM 2024) — OS 调度抖动可引入 2-5ms 帧延迟

### 音频：40ms 固定环形缓冲

- 深度：4 个 Opus 帧 (40ms)
- 依据：scrcpy 默认 50ms，LAN 场景 40ms 为合理折中
- 空 buffer 时：调用 Opus PLC（`opus_decode(NULL, 0)`）生成补偿帧
- 满 buffer 时：丢弃最旧帧
- 依据：Moonlight 用 Opus PLC 处理丢包，效果优于静音插入

## CoreAudio 音频输出

### 架构

- API：AudioUnit (`kAudioUnitSubType_DefaultOutput`)
- 回调模型：Render callback (pull model) — CoreAudio 唯一模式
- Buffer 大小：256 samples (~5.3ms callback interval)
- 格式：Float32, 48kHz, Stereo
- 线程：CoreAudio 自动提升为实时线程，无需手动设置优先级

### 数据流

```
Opus decode → PCM Float32 → 环形 buffer (40ms)
                                    ↓
CoreAudio render callback ← 每 5.3ms 拉取 256 samples
```

### Underrun 处理

1. buffer 为空时：调用 Opus PLC 生成 10ms 补偿帧填入 buffer
2. 连续 underrun >3 次：日志告警，临时扩大 buffer 至 60ms
3. 恢复正常后自动收缩回 40ms
